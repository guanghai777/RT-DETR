# 消融实验计划（improve.yaml）

> 对象：`ultralytics/cfg/models/rt-detr/improve/improve.yaml`
> 参考：`/home/pan/Documents/论文材料/方法1/基于改进RT-DETR的轻量化绝缘子检测0718.docx` 表 3 的消融做法
> 日期：2026-11-23
> 核心调整：把 **MFM + MANet 合并为一个“颈部”因素**，消融从 4 因素 17 组降到 **3 因素 8 组 + 1 组宽度对照**。

---

## 0. 结论：4 个改进压成 3 个因素

### 0.1 合并方案

| 原改进 | 消融因素 | 说明 |
| --- | --- | --- |
| C2f_LSBlock 主干 | **A** | 保留为独立因素 |
| TransformerEncoderLayer_DPB | **B** | 保留为独立因素 |
| MFM（替代 Concat） | **C** | 与 MANet 合并为“颈部”因素 |
| MANet（替代 RepC3） | **C** | 同上 |

于是得到 3 个二值因素：

| 因素 | ×（关） | √（开） |
| --- | --- | --- |
| A | ResNet18 主干 | **C2f_LSBlock** 主干 |
| B | AIFI | **TransformerEncoderLayer_DPB** |
| C | Concat + RepC3 | **MFM + MANet** |

### 0.2 为什么是 MFM + MANet，而不是别的两个

1. **位置相同**：MFM 和 MANet 都在 FPN/PAN 颈部，且是相邻层——MFM 替换 `Concat`，MANet 替换 `RepC3`。它们共同构成“颈部多尺度融合”的一次改造。
2. **功能相同**：两者都在处理“不同尺度特征如何对齐、融合、聚合”；单独讲 MFM 或 MANet 都只是半个颈部故事。
3. **和 0718 论文的表结构对得上**：论文的 B=RFPN 本身就是一个颈部结构，而不是两个独立模块。把 MFM+MANet 作为一个“颈部”因素，正好让新论文也回到“主干 + 编码器 + 颈部”三段式。
4. **叙事更干净**：三个贡献分别是“轻量主干”“P5 全局编码”“多尺度融合颈部”，和论文的三段式结论一一对应。

### 0.3 为什么不合并别的组合

| 候选合并 | 问题 |
| --- | --- |
| LSBlock + DPB | 一个在主干、一个在 P5 编码器，跨阶段；且 LSBlock 是最大的轻量化改动，合并会掩盖它的参数/精度贡献 |
| DPB + MFM | 一个是全局自注意力，一个是跨尺度通道门控，功能不同，合在一起说不清“到底改了什么” |
| LSBlock + MFM | 同上，跨阶段且功能不同 |
| **MFM + MANet** | **同位置、同功能、天然是一个颈部改造**，最合适 |

### 0.4 合并的代价与补救

代价：主表只能回答“颈部整体有没有用”，不能直接回答“MFM 和 MANet 各自贡献多少”。

补救：如果审稿人追问，在最终方法（A=B=1）的上下文里补一个 **2×2 颈部子消融**，只需要多跑 **2 组**：

| 颈部组合 | 配置 | 是否已在主表 |
| --- | --- | --- |
| Concat + RepC3 | A=B=1，即主表第 5 行 | 已有 |
| **MFM + RepC3** | 新建 | 新增 1 组 |
| **Concat + MANet** | 新建 | 新增 1 组 |
| MFM + MANet | A=B=1，即主表第 8 行 | 已有 |

由此可以算：

- MFM 主效应 = `mAP(MFM+RepC3) - mAP(Concat+RepC3)`
- MANet 主效应 = `mAP(Concat+MANet) - mAP(Concat+RepC3)`
- 两者交互 = `mAP(MFM+MANet) - mAP(MFM+RepC3) - mAP(Concat+MANet) + mAP(Concat+RepC3)`

所以主表 9 组，必要时加到 11 组；比 4 因素全因子的 17 组省很多。

### 0.5 最终组数

| 方案 | 组数 | 说明 |
| --- | ---: | --- |
| 主表（3 因素全因子 + 宽度） | **9** | 8 组全组合 + 1 组 X3=128 |
| 主表 + 颈部子消融 | 11 | 补 2 组拆 MFM/MANet |
| 原 4 因素全因子 | 17 | 只在有余力时做附录 |

### 1.1 要回答的问题

### 2.3 `val.py` 逐类表类别名错位（P0）

`val.py:48` 用 `length = result.box.p.size` 取“有实例的类数”（本数据集是 6），但 `val.py:49` 的 `model_names = list(result.names.values())` 是按 7 类排的。class 2 缺失后，从第 3 行开始类别名全部错位：

## 3. 前置条件（P0 环境门禁）

### 3.1 LSBlock 的 torch.amp 兼容性

现象：首次 forward 报 `NameError: name 'SkaFn' is not defined`。

原因：torch≥2.4 的 `torch.amp.custom_fwd` 必须带 `device_type`；`lsnet.py` 里裸用 `@custom_fwd`，在类定义时抛 `TypeError`，被外层 `except` 吞掉，`SkaFn` 没有定义。

最小修复（`ultralytics/nn/backbone/lsnet.py` 顶部）：

```python
from functools import partial
try:
    from torch.amp import custom_fwd as _cf, custom_bwd as _cb
    custom_fwd = partial(_cf, device_type='cuda')
    custom_bwd = partial(_cb, device_type='cuda')
except Exception:
    from torch.cuda.amp import custom_fwd, custom_bwd
```

`ultralytics/nn/backbone/lsnet.py` 不在 git 跟踪范围，把 patch 存到 `scripts/patches/lsnet-torch-amp.patch` 并在部署指南记录。

### 3.2 Triton 与 C 编译器

SKA 是 Triton kernel，CPU / 无编译器不可用。本机 `gcc/cc` 不在 PATH；如果改用 4090D，先在那边确认 `gcc --version` 可用。

二选一：

1. 安装编译器：`sudo apt install build-essential`；或 conda 装 `gcc_linux-64 gxx_linux-64` 并导出 `CC/CXX`。
2. 实在装不了：用等价 PyTorch 实现替换 `SKA.forward`，但必须先在 GPU 上与 Triton 版对拍，且所有含 LSBlock 的组统一用同一实现；FPS 只在 Triton 版上测。

验收不是“能 import”，而是 **640 forward + 1 个 optimizer step（backward）不报错**。

### 3.3 DPB 只支持 640

`TransformerEncoderLayer_DPB` 在 `transformer.py:993` 把 `group_size` 写死为 `(20, 20)`。全部固定 640；不要多尺度、TTA、动态 shape。

### 3.4 环境完整性

本机当前状态：

- `mujoco310` 有 torch 2.11.0+cu128、triton 3.6.0，但**没有 cv2**；
- `detect` 环境没有 torch；
- 没有 `gcc/cc`。

不要直接用这两个环境开跑。按 `docs/部署指南.md` 建完整环境，至少通过：


`scripts/check_env.py` 只构建 `improve-method1.yaml` 且不做 forward，查不出 LSBlock/DPB 的问题。

### 3.5 默认模型口径

## 4. 实验设计：3 因素全因子（8 + 1 组）

### 4.1 主表

固定 **X3=256**，对 A/B/C 做 `2^3 = 8` 组；最后单独跑一组全模块 + X3=128（当前 improve.yaml）。

| 序号 | A LSBlock | B DPB | C MFM+MANet | X3 | 组合 | 配置来源 | 目的 |
| ---: | :---: | :---: | :---: | ---: | --- | --- | --- |
| 1 | × | × | × | 256 | 基线 | `rtdetr-r18.yaml` | r18 + AIFI + Concat + RepC3 |
| 2 | √ | × | × | 256 | A | `rtdetr-C2f-LSBlock.yaml`（nc→7） | 主干主效应 |
| 3 | × | √ | × | 256 | B | `rtdetr-AIFI-DPB.yaml`（nc→7） | 编码器主效应 |
| 4 | × | × | √ | 256 | C | `rtdetr-MFM-MANet.yaml`（nc→7，X3→256） | 颈部主效应 |
| 5 | √ | √ | × | 256 | AB | 新建 `F110-lsblock-dpb.yaml` | A/B 交互 |
| 6 | √ | × | √ | 256 | AC | 新建 `F101-lsblock-neck.yaml` | A/C 交互 |
| 7 | × | √ | √ | 256 | BC | 新建 `F011-dpb-neck.yaml` | B/C 交互 |
| 8 | √ | √ | √ | 256 | ABC | 新建 `F111-all-x3-256.yaml` | 全模块（256） |
| 9 | √ | √ | √ | **128** | ABC-128 | `improve.yaml` | 宽度对照 |

这张表就是 0718 论文表 3 的 3 因素版本：同样是“×/√ + 全组合 + P/R/mAP/FLOPs/Params”，只是模块名换成“主干 / 编码器 / 颈部”。

### 4.2 需要新建/改动的配置

目录建议：`ultralytics/cfg/models/rt-detr/ablation/`，全部 `nc: 7`。

| 文件 | 生成方式 |
| --- | --- |
| `F000-r18.yaml` | 复制 `rtdetr-r18.yaml` |
| `F100-lsblock.yaml` | 复制 `rtdetr-C2f-LSBlock.yaml`，`nc: 80` → `nc: 7` |
| `F010-dpb.yaml` | 复制 `rtdetr-AIFI-DPB.yaml`，`nc: 9` → `nc: 7` |
| `F001-neck.yaml` | 复制 `rtdetr-MFM-MANet.yaml`，`nc: 80` → `nc: 7`，第 19 层 `MANet [128,...]` → `[256,...]` |
| `F110-lsblock-dpb.yaml` | 从 `F100` 把第 10 层 `AIFI` → `TransformerEncoderLayer_DPB` |
| `F101-lsblock-neck.yaml` | 从 `F100` 把 14/19/22/25 层 `Concat` → `MFM [256]`，15/20/23/26 层 `RepC3` → `MANet [256, False, 2, 3]` |
| `F011-dpb-neck.yaml` | 从 `F001` 把第 10 层 `AIFI` → `TransformerEncoderLayer_DPB`（X3 已是 256） |
| `F111-all-x3-256.yaml` | 从 `improve.yaml` 把第 20 层 `MANet [128,...]` → `[256,...]` |
| `F111-all-x3-128.yaml` | 复制 `improve.yaml` |

逐项 diff 说明：

- **B（DPB）**：`- [-1, 1, AIFI, [1024, 8]]` → `- [-1, 1, TransformerEncoderLayer_DPB, [1024]]`
- **C 的 MFM**：第 14/19 层 `[[-2, -1], 1, Concat, [1]]` → `[[-2, -1], 1, MFM, [256]]`；第 22 层 `[[-1, 16], 1, Concat, [1]]` → `[[-1, 16], 1, MFM, [256]]`；第 25 层 `[[-1, 11], 1, Concat, [1]]` → `[[-1, 11], 1, MFM, [256]]`
- **C 的 MANet**：第 15/20/23/26 层 `RepC3 [256, 0.5]` → `MANet [256, False, 2, 3]`
- **X3**：只改第 20 层 MANet 的 c2，256 ↔ 128

注意：MANet 的 `[256, False, 2, 3]` 中，`False` 是 shortcut，`2` 是 p，`3` 是 kernel_size；n=3 来自 repeats 列，不要手动把 `2` 当 n 改掉。

### 4.3 可选：颈部 2×2 子消融（多 2 组）

如果审稿人问“到底是 MFM 有用还是 MANet 有用”，在 A=B=1 的上下文里补：

| 编号 | 颈部组合 | 配置 | 新增 |
| --- | --- | --- | --- |
| N0 | Concat + RepC3 | = 主表第 5 行 | 已有 |
| N1 | **MFM + RepC3** | 新建 `N-mfm-repc3.yaml` | +1 |
| N2 | **Concat + MANet** | 新建 `N-concat-manet.yaml` | +1 |
| N3 | MFM + MANet | = 主表第 8 行 | 已有 |

分析：

- MFM 主效应 = `mAP(N1) - mAP(N0)`
- MANet 主效应 = `mAP(N2) - mAP(N0)`
- 交互 = `mAP(N3) - mAP(N1) - mAP(N2) + mAP(N0)`

主表 9 组 + 子消融 2 组 = 11 组。

### 4.4 分析口径

1. **主效应**：第 2–4 行 vs 第 1 行，分别看 A/B/C 单独加入的效果。
2. **两两交互**：
   ```
   I_XY = mAP(XY) - mAP(X) - mAP(Y) + mAP(∅)
   ```
   - `I > 0`：协同；
   - `I < 0`：拮抗（0718 论文的 AB 行就是负交互，要如实写）；
   - `I ≈ 0`：近似可加。
3. **全模块**：第 8 行 vs 第 5–7 行，看三个一起用是否最优。
4. **成本**：每行 Params/FLOPs 相对基线的变化；A 降参数、C 升参数，避免把“整体轻量”错误归因给所有模块。
5. **宽度**：第 9 行 vs 第 8 行；若 128 的 mAP 掉得少且成本明显低，选 128 作为轻量版。
6. **可选颈部拆解**：§4.3 的 2×2。

## 5. 执行流程

### Phase 0：环境与配置门禁（约 0.5–1 天）

1. 按 §3 修 `lsnet.py` 的 `custom_fwd/custom_bwd`，装编译器或确定 fallback。
2. 建完整训练环境，确认 `cv2/torch/triton` 都能 import。
3. 修 `val.py` 的类别名错位，加 `--name`；给 `train.py` 加 `--seed`。
4. 按 §4.2 建 9 个配置，全部 `nc: 7`。
5. 逐配置做 **640 forward** 和参数统计：

```bash
python - <<'PY'
import torch, warnings
warnings.filterwarnings('ignore')
from ultralytics import RTDETR
from ultralytics.utils.torch_utils import model_info

cfgs = [
    'ultralytics/cfg/models/rt-detr/ablation/F000-r18.yaml',
    'ultralytics/cfg/models/rt-detr/ablation/F100-lsblock.yaml',
    # ... 其余配置
]
for cfg in cfgs:
    m = RTDETR(cfg)
    m.model.eval().cuda()
    with torch.no_grad():
        m.model(torch.zeros(1, 3, 640, 640).cuda())
    print(cfg, model_info(m.model))
PY
```

> 这个脚本会触发 LSBlock 的 forward；如果报 `SkaFn` 或 Triton/编译器错误，回到 §3。

### 6.3 结论判定规则

- 单因素行如果 mAP 不升但成本大降（尤其 A），定位为“轻量化贡献”，不要硬说精度提升。
- 两两/三模块交互为负时，如实写“存在拮抗”，并解释可能原因。

- X3 宽度：若 128 的 mAP50-95 与 256 差距 ≤ 0.3 且成本明显低，选 128；若稀有类掉 > 2 个点，选 256。
- 颈部子消融：如果 MFM 或 MANet 单独效果很弱、只有组合才有效，说明两者是互补关系，不是冗余。

## 7. 论文写作注意事项

1. **基线口径**：写明基线是 `rtdetr-r18`（解码器 3 层）、所有组从零训练、同一超参、同一 split。
2. **区分两套数据**：0718 论文是 9 类 7972 张，当前是 7 类 2150/391/287；只借鉴设计，不混用表 3 数值。
3. **三段式叙事**：把改进写成“轻量主干（A）+ P5 全局编码（B）+ 多尺度融合颈部（C=MFM+MANet）”，和论文的三段式结论对齐。
4. **轻量化归因**：主干约 −6.6M，颈部约 +1.8M（MANet 比 RepC3 重），解码器基本持平。不要笼统写“整体轻量化来自所有模块”。
5. **模块来源与位置**：MFM 出自 DCMPNet（原用于去雾），MANet 出自 Hyper-YOLO（原在 backbone，这里移到 neck）。写清“借鉴自哪里、用在哪里、做了哪些适配”。
6. **数据事实**：`broken_disc` 0 实例；`val`/`test` 映射与常规相反；主表用 `images/val`(391)。
7. **交互分析**：用 `I_XY` 公式给出正/负交互，不要只说“组合更好”。0718 论文自己也有 AB 负交互的例子。
8. **单 seed 局限**：只有 1 个 seed 时，不要用“显著”描述 < 1 个点的差异。

## 9. 风险与应对

| 风险 | 触发条件 | 应对 |
| --- | --- | --- |
| LSBlock 无法 forward | `SkaFn` NameError / Triton 编译失败 | 按 §3.1/§3.2 修；实在不行用 PyTorch fallback，全组统一 |
| 640 以外尺寸报错 | 改 `--imgsz` / TTA / 动态导出 | 全部固定 640 |
| 6GB OOM | batch 8/16/32 | 2060 用 batch 4；4090D 用 32；同一张表固定 |
| 训练 NaN/不收敛 | LSBlock 自定义 backward / 数据异常 | 检查 `results.csv` 前几个 epoch；先跑基线确认数据管线 |
| 类别名错位 | 未修 `val.py` | 按 §2.3 修，逐类表用 `ap_class_index` |
| `best.pt` 选模泄漏 | 用 `images/test` 选模又报它 | 主表用 `--split test`（`images/val`） |
| 颈部合并被质疑 | 审稿人问 MFM/MANet 各自贡献 | 补 §4.3 的 2 组 2×2 子消融 |
| 结果差异很小 | 单 seed / 稀有类样本少 | 补 seed；报告 mean±std；结论降级为“趋势” |
| 配置漂移 | 手写配置出错 | 每个文件头写“开了哪几位”；开跑前和上一组 diff |
